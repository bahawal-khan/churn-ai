Since `random_forest_v1` is the only model with `selected_as_recommended_production_model: true`, `ml/models/explain.py`'s runnable script (`main()`) builds and persists `global_shap.json` only for it — mirrors Phase 5's own rule that `test_evaluated`/artifact generation happens once, for the actual winner, not speculatively for every baseline (`ml/models/MODELS.md` §9).

## 2. Output-space caveat (verified empirically, not assumed)

SHAP's defining additivity property — `sum(shap_values) + base_value == model_output` — only holds exactly in whichever space a given explainer natively operates in:

| Algorithm / Explainer | Additive in | Verified |
|---|---|---|
| `random_forest` / `TreeExplainer` | **Predicted probability**, directly | Exact — diff `0.000000` (§4 below) |
| `gradient_boosting` / `TreeExplainer` | Raw log-odds (`sigmoid(sum + base) == predict_proba`, not the sum directly) | Confirmed against `gradient_boosting_v1` |
| `logistic_regression` / `LinearExplainer` | Raw log-odds (`decision_function`, not `predict_proba`) | Confirmed against `logistic_regression_v1` |
| `ann` / `GradientExplainer` | Approximately probability (expected-gradients sampling approximation, even though the model's own output is already sigmoid) | Confirmed within a few percentage points, not exact |

This is why `global_shap.json` and every local-explanation payload carry an `additivity_space` field rather than silently normalizing every algorithm into one space — doing that normalization for the log-odds-additive models would misrepresent individual feature contributions. It's a real, stated limitation, in the same spirit as `ml/models/MODELS.md` §10's Random Forest artifact-size tradeoff: reported honestly rather than papered over. It's currently latent for the actual production artifact, since Random Forest is exactly probability-additive.

## 5. Disclaimer

Every explanation payload (global and local) carries `disclaimer`, sourced from a single constant (`ml.config.SHAP_DISCLAIMER`) rather than being retyped per call site, verbatim from `PROJECT_SPEC.md` §15:

> "This shows what the model learned from patterns in the data — it identifies correlation, not proven causation."

## 6. Verifying explanations are real, not hard-coded (`ML_SPEC` §13's "never hard-coded" rule)

Two checks enforce this, both exercised in `tests/ml/test_explain.py` against the real fitted models (not mocks):

1. **Additivity** (`verify_additivity`) — SHAP's defining mathematical property. A hard-coded or templated "explanation" would not satisfy `sum(shap_values) + base_value == model_output` for an arbitrary real input; the actual SHAP library output does, exactly, for the Random Forest case (§4 above).
2. **Non-determinism across different inputs** (`test_local_explanation_random_forest_not_hardcoded_across_different_inputs`) — two different customers' local explanations are asserted to differ. A static/templated explanation would return the same values regardless of input; this confirms the values are actually computed per-row.

## 9. Scope note

This phase computes global and local SHAP explanations for the selected production model and persists the global summary as a versioned artifact, per `ML_SPEC` §13. It does not build the Flask backend endpoint that would serve local explanations on-demand per prediction request, the `explanations` DB table itself, or any frontend rendering of SHAP output — all explicitly Phase 7+ scope (`BACKEND_SPEC.md`, `DATABASE_SPEC.md` §2.10, `FRONTEND_SPEC.md`).
