# Phase 3 Feature Engineering Findings

Generated by `ml/features/engineer.py` (`FeatureEngineer`) run against the combined development dataset (`combined_development_dataset.csv`, 21,043 rows). All numbers below are computed directly from that file via `ml/features/feature_engineering_report.json`, not assumed (`docs/ML_SPEC.md` §2.7 discipline, applied here per §4).

Every feature is a per-row derivation — none involve a dataset-level aggregate statistic — so `FeatureEngineer.fit` is stateless and there is no train/test leakage risk to manage in this phase (`docs/ML_SPEC.md` §4).

## `CLTV` — deferred, not engineered here

Per `ml/eda/FINDINGS.md` (Phase 2), `CLTV` exists only on the IBM source (correlation with target: -0.1275, below the 0.5 leakage-suspicion threshold, so it is a legitimate candidate feature) but is structurally absent for the Pakistan-Synthetic and India-Synthetic sources. Folding it into the combined dataset requires an imputation strategy for the two-thirds of rows where it doesn't exist — that is a preprocessing decision (`docs/ML_SPEC.md` §5: `SimpleImputer`), not a feature-engineering one, and preprocessing is explicitly out of Phase 3 scope. `CLTV` therefore remains excluded from `ml.config.MODELING_COLUMNS` and is not touched by `FeatureEngineer`. The inclusion decision is deferred to whichever phase builds the `ColumnTransformer` preprocessing pipeline.

## Rejected feature candidates

No new candidates were considered/rejected beyond those already recorded in `ml/eda/FINDINGS.md` (raw `CustomerID`/geo columns, `Churn Score`, `Churn Reason`) — Phase 2's rejections stand; Phase 3 did not introduce or reject any additional candidates.

## Leakage prevention

`FeatureEngineer` computes every output column row-wise from that row's own input columns only — no feature is derived from a dataset-level mean, rate, or other aggregate statistic that would need to be fit on a training split. Consequently there is nothing in this phase that could leak information from validation/test rows into training rows: `fit()` is a no-op, and `transform()` output for any given row is provably independent of what other rows are present in the same call (verified by `tests/ml/test_feature_engineering.py::test_transform_output_independent_of_fit_data`). The train/validation/test split itself (`docs/ML_SPEC.md` §6) is out of Phase 3 scope and is not implemented here.

## Reproducibility

`FeatureEngineer` is an `sklearn.base.BaseEstimator`/`TransformerMixin` subclass (`ml/features/engineer.py`), so it composes directly into the `Pipeline` that a later phase builds around it (`docs/ML_SPEC.md` §4: "implemented as sklearn-compatible custom transformers... composed into the same pipeline as preprocessing"). This module does not itself build that `ColumnTransformer`, perform imputation/encoding/scaling, or run a train/test split — those remain explicitly out of scope until the phase that owns them.
