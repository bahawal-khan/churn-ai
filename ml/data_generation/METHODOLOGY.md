# Phase 1 — Dataset Foundation: Methodology & Limitations

Companion to `docs/PROJECT_SPEC.md` §3 and `docs/ML_SPEC.md` §1. Records
exactly what was built for Phase 1, how it was validated, and what it does
and does not prove.

## What this phase produced

1. **IBM Telco audit** (`ml/eda/ibm_audit.py`) — re-derives shape, dtypes,
   missing values, duplicates, leakage columns, and class balance directly
   from `data/raw/IBM_Telco_customer_churn_IBM_dataset.csv` and cross-checks
   every number against the facts already documented in
   `docs/PROJECT_SPEC.md` §2.1. All facts confirmed
   (`ml/eda/ibm_audit_report.json`).
2. **Synthetic Pakistan generator** (`ml/data_generation/pakistan_generator.py`)
   — 7,000 records across 6 archetypes.
3. **Synthetic India generator** (`ml/data_generation/india_generator.py`)
   — 7,000 records across 6 archetypes.
4. **Combined development dataset** (`ml/data_generation/combine.py`) —
   IBM (7,043) + Pakistan-Synthetic (7,000) + India-Synthetic (7,000) =
   **21,043 records**, written to
   `data/processed/combined_development_dataset.csv` with a `Source`
   provenance column on every row.
5. **Generator validation** (`ml/data_generation/validate.py`) —
   churn-rate-by-country and churn-rate-by-archetype tables, plus a sanity-
   check logistic regression.

## Generation methodology

Both country generators share one engine (`ml/data_generation/engine.py`)
so the mechanics are identical; only each archetype's distributions and
conditional probabilities differ, and they are defined separately in each
generator file. Per archetype:

- **Numeric features** (`Tenure Months`, `Monthly Charges`) are drawn from
  archetype-specific truncated-normal distributions clipped to the ranges
  actually observed in the IBM data (0-72 months, $18.25-$118.75).
- **`Total Charges`** is `tenure x monthly_charge + billing-variance noise`
  (never a perfectly deterministic product), floored at 0 and forced to 0
  for zero-tenure customers.
- **Categorical features** (`Contract`, `Internet Service`, add-ons,
  `Payment Method`, etc.) are drawn from archetype-specific conditional
  probability tables, not one global distribution.
- **No row duplication or jittering of IBM rows** — every record is
  synthesized directly from its archetype's distributions.
- **Churn labels** are generated by a latent-propensity model
  (`docs/PROJECT_SPEC.md` §3.5): a logistic function of contract type,
  normalized charges, normalized tenure, tech-support status, payment
  method, and family ties, plus a per-archetype base-churn offset and
  Gaussian noise (`EPSILON_STD = 1.15`), then sampled as a Bernoulli draw.
  Weight signs match the churn intuition confirmed by the IBM audit; exact
  weight values are documented as constants in `engine.py`, not tuned
  against any real Pakistani/Indian outcome data (none exists in this
  project).
- **Reproducibility** — `ml/config.py` defines `RANDOM_SEED = 42`, with
  distinct derived per-country seeds (`PAKISTAN_SEED`, `INDIA_SEED`) so the
  two countries' outputs are not accidentally correlated (they would be if
  both used the same seed, since several conditional draws — e.g. the 50/50
  `Gender` split — share the same call shape across countries). Re-running
  a generator with its seed reproduces byte-identical output
  (`tests/ml/test_generators.py::test_deterministic_same_seed_byte_identical`).

## Validation results (`ml/data_generation/validation_report.json`)

| Check | Result |
|---|---|
| Overall combined synthetic churn rate in 20-35% band | 32.4% — pass |
| Pakistan churn rate in band | 31.4% — pass |
| India churn rate in band | 33.4% — pass |
| Sanity-check logistic regression AUC in 0.75-0.90 band | 0.762 — pass |
| All 6 expected coefficient signs match domain intuition | pass |
| No single feature reaches near-1.0 standalone AUC (ceiling 0.95) | max 0.671 — pass |
| No archetype is a pure 0%/100% churn bucket | pass |

Per-archetype churn rates span roughly 7% (urban/metro high-income) to 69%
(young urban single, high-churn) — the intended wide, overlapping spread
that keeps churn learnable but not trivially separable by any single rule.

Re-run validation: `python -m ml.data_generation.validate`

## Limitations (binding — see `docs/PROJECT_SPEC.md` binding cross-cutting rules)

- **The synthetic Pakistani and Indian data is not evidence of real-world
  accuracy for customers in those countries.** Archetype shares,
  distributional parameters, and payment-method mixes are illustrative
  assumptions written by this project, not derived from market research or
  observed data. This is explicitly documented, not implied otherwise
  anywhere in the product (`docs/PROJECT_SPEC.md` §3.6).
- **`Country`/`Source` is metadata only.** It is carried on every row for
  EDA, stratified sampling, and provenance, and is structurally excluded
  from the feature set of any model that gets promoted to active/production
  status (`docs/ML_SPEC.md` §1).
- **India's archetype characteristics mirror Pakistan's role-for-role**
  (e.g. "metro high-income" plays the same structural role as "urban
  high-income") because `docs/PROJECT_SPEC.md` §3.4 specifies India's
  archetype names/shares but not distinct behavioral characteristics beyond
  "same methodology, distinct archetypes." Distributional *parameters*
  differ between the two generators (not copy-pasted values) — see
  `india_generator.py`'s module docstring for the specific deltas — but the
  qualitative segment story is deliberately parallel.
- **The IBM audit here is structural only** (shape, dtypes, missingness,
  duplicates, leakage, cardinality, class balance) — it does not include
  distribution visuals, correlation analysis, or cross-source comparison.
  Those are Phase 2 deliverables (`docs/ML_SPEC.md` §2), out of scope here.
- **The sanity-check logistic regression is a generator-validation tool,
  not a churn model.** It is fit on raw, unencoded, unsplit synthetic data
  purely to confirm the latent-propensity mechanism produces learnable,
  non-trivial, correctly-signed relationships — it has no train/test split,
  no preprocessing pipeline, and is never serialized or used for
  prediction. The real baseline model comparison happens in Phase 4.
