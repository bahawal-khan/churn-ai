# Phase 4 Preprocessing & Data Splitting Findings

Generated by `ml/preprocessing/split.py` against the combined development dataset (`combined_development_dataset.csv`, 21,043 rows). All numbers below are computed directly from `ml/artifacts/preprocessing_dev/metadata.json`, not assumed (`docs/ML_SPEC.md` §2.7 discipline, applied here per §5/§6).

## Train / validation / test split (`docs/ML_SPEC.md` §6)

Stratified two-key split on `(Source, Churn Value)`, ratio 70/15/15, fixed seed (`RANDOM_SEED = 42`).

| Split | Rows | Share | Churn rate | IBM | Pakistan-Synthetic | India-Synthetic |
|---|---|---|---|---|---|---|
| Train | 14,729 | 69.99% | 30.45% | 4,931 | 4,900 | 4,898 |
| Validation | 3,157 | 15.00% | 30.44% | 1,056 | 1,050 | 1,051 |
| Test | 3,157 | 15.00% | 30.44% | 1,056 | 1,050 | 1,051 |
| **Total** | **21,043** | 100% | 30.45% (overall) | 7,043 | 7,000 | 7,000 |

Churn rate and per-source share are within 0.02% of the overall dataset values in every split — the two-key stratification is working as intended (`docs/ML_SPEC.md` §6: "so IBM/PK-synthetic/IN-synthetic are proportionally represented in every split"). Splits are row-disjoint and their union reconstructs the full 21,043-row dataset exactly (`tests/ml/test_preprocessing.py::test_splits_are_disjoint_and_reconstruct_full_dataset`). The split is reproducible: re-running with the same seed produces byte-identical `CustomerID` membership per split (`test_split_is_reproducible_with_fixed_seed`).

The test split is written to `data/processed/splits/test.csv` but is not evaluated against in this phase — per ML_SPEC §6 it is touched exactly once, for final reported metrics, in whichever later phase does that reporting.

## Preprocessing pipeline (`docs/ML_SPEC.md` §5)

`ml/preprocessing/pipeline.py` composes `ml.features.engineer.FeatureEngineer` (Phase 3) with a `ColumnTransformer`:

```
Pipeline(
  feature_engineering: FeatureEngineer()                              # Phase 3, unchanged
  column_transform:    ColumnTransformer(
                          numeric:      SimpleImputer(median) -> StandardScaler   [scale=True only]
                          categorical:  SimpleImputer(most_frequent) -> OneHotEncoder(handle_unknown="ignore")
                        )
)
```

Two variants are built from the same definition and both are fit on the training split and serialized:

- `pipeline_scaled.joblib` — numeric branch scaled (`StandardScaler`), for Logistic Regression / the ANN.
- `pipeline_unscaled.joblib` — numeric branch not scaled, for tree-based baselines (Random Forest / Gradient Boosting), sharing identical imputation/encoding with the scaled variant so baseline comparisons stay apples-to-apples on the same engineered feature set (`docs/ML_SPEC.md` §5).

No model is trained by this phase — only the preprocessing pipelines are fit and serialized.

## Feature count before / after preprocessing

| Stage | Count |
|---|---|
| Raw modeling columns (`ml.config.MODELING_COLUMNS`) | 19 |
| After feature engineering (Phase 3 columns added) | 28 (5 numeric + 23 categorical) |
| After preprocessing (impute + one-hot encode + scale) | **64** |

The jump from 28 to 64 is entirely from one-hot expansion of the 23 categorical columns (16 raw + `has_internet`, `has_protection_addon`, `has_streaming_addon`, `contract_risk_flag`, `payment_risk_flag`, `family_flag`, `tenure_group`); the 5 numeric columns (`Tenure Months`, `Monthly Charges`, `Total Charges`, `active_addon_count`, `avg_monthly_value`) pass through 1:1. Both the scaled and unscaled pipeline variants produce the same 64-column output shape — only the numeric values differ (`test_scaled_and_unscaled_pipelines_produce_same_feature_count`).

`CLTV` remains excluded: it is not part of `ml.config.MODELING_COLUMNS` and does not exist as a column in `combined_development_dataset.csv` at all (structurally absent for the two synthetic sources, per `ml/features/FEATURES.md`), so there was no imputation decision to make for it in this phase.

## Leakage checks

Structural, not conventional — `ml.preprocessing.pipeline.NUMERIC_COLUMNS` / `CATEGORICAL_COLUMNS` are the *entire* allowlist passed to `ColumnTransformer`; anything not named there cannot reach a fitted model even if left in an input DataFrame.

| Check | Result |
|---|---|
| `Source` present in pipeline input columns | **No** — used only for stratification, never a feature (`PROJECT_SPEC.md` binding rule) |
| `CustomerID` present in pipeline input columns | **No** |
| `Churn Value` (target) present in pipeline input columns | **No** |
| `Churn Score` / `Churn Reason` / `Churn Label` present in combined dataset at all | **No** — already excluded before Phase 1's combined dataset was built |
| Pipeline fit only on training split; val/test only `.transform()`-ed | **Yes** — `pipeline.fit_transform(train[...])` then `pipeline.transform(val[...])` / `.transform(test[...])`, never fit on val/test |
| Unseen category at inference time (e.g. a payment method never seen in training) | Handled gracefully via `OneHotEncoder(handle_unknown="ignore")` — degrades to an all-zero encoding rather than raising (`test_pipeline_handles_unseen_category_gracefully`) |

## Scope note

This phase builds and fits the preprocessing pipeline and produces the train/validation/test splits. It does not train, evaluate, or compare any model (Logistic Regression, Random Forest, Gradient Boosting, or ANN) — that is out of scope here per `CLAUDE.md`'s phase-scoping rule.
